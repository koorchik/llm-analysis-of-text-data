# SUMMARY 2026-08-08 — Four-arm Ψ_link comparison (local vs cloud judges, union blocker)

Extends the two committed baselines with two new streaming (`FLOW=incremental`) arms that turn the
**union blocker on** (`CANDIDATE_GENERATOR=union`, `EMBEDDINGS=1`, local `embeddinggemma`), varying only
the **judge model**: a local `gemma4:e4b-32k` and a cloud reasoning model `gpt-5-6-sol` (via a free
LiteLLM proxy). All four arms run the same frozen 204-doc gpt-5 extractions and are scored on the
`test` split of `gold/gold.json` (`gold-aliases-v2`, provisional — queue-3 rows unreviewed).

## Key findings

1. **The repair phase, not the linker, is the differentiator.** All local/union arms mint aggressively
   (e4b 88%, gpt-5-6-sol 96% mint) and rely on phase-2 `StreamingRepairer` to merge post-hoc. gpt-5-6-sol's
   repair-judge emits clean JSON and merged successfully (pairwise F1 0.599); `gemma4:e4b-32k`'s repair-judge
   fails the `reviews` schema on large prompts (~50%+ format errors) so its merges never land (F1 0.290).
   The core `link-judge` was clean on both.
2. **Only gpt-5-6-sol bridged cross-lingual pairs** (stratum b: P=1.0, R=0.5; Росія↔Russia). Every other arm
   scored R(b)=0. This needs the dense channel **with glosses** — and only the strong judge writes glosses
   (`EntityRegistry.mint extras.gloss`); on the local judge the dense channel is name-only, so script-bridging
   didn't land even with the union blocker on.
3. **The new local arm still beats the old local baseline** (0.290 vs 0.177): union blocker + `e4b` + 32k
   context helped, but it remains well below the cloud arms — it is the **$0, ~3.5h deployable** point.
4. **gpt-5-6-sol is a quality ceiling, not a deployable system:** ~37h wall-clock for 204 docs (reasoning
   model × two dependent repair calls per doc, repair-judge calls up to ~13 min). Fine as a reference arm.
5. Embedding-model bench (`embed-bench-2026-08-08`, name+gloss, recall@20): **embeddinggemma 84.7%** >
   qwen3-embedding:4b 77.7% > bge-m3 69.5%. embeddinggemma also co-resides trivially (621 MB), so it was the
   dense channel for both new arms.

## Reproduction

`.env` must set `STEPS="streamingPipeline"`. Pre-seed frozen extractions per `docs/RUN-STREAMING.md` §4.

```bash
# local arm
STEPS=streamingPipeline FLOW=incremental CONDITION=psi-link-gemma-e4b-union \
  LLM_PROVIDER=ollama LLM_MODEL=gemma4:e4b-32k \
  CANDIDATE_GENERATOR=union EMBEDDINGS=1 EMBEDDINGS_PROVIDER=ollama EMBEDDINGS_MODEL=embeddinggemma \
  DECISIONS_LOG=1 npm start

# cloud arm (OpenAI-compatible proxy; OPENAI_BASE_URL is read by the openai SDK, no code change)
STEPS=streamingPipeline FLOW=incremental CONDITION=psi-link-gpt56sol-union \
  LLM_PROVIDER=openai LLM_MODEL=gpt-5-6-sol \
  OPENAI_BASE_URL=https://openai.corewars.cc/v1 OPENAI_API_KEY=<proxy-key> \
  CANDIDATE_GENERATOR=union EMBEDDINGS=1 EMBEDDINGS_PROVIDER=ollama EMBEDDINGS_MODEL=embeddinggemma \
  DECISIONS_LOG=1 npm start

# score + view
npm run evaluate -- --gold gold/gold.json --split test --run <runDir> --json <runDir>/results.json
npm run replay   -- --in <runDir>/decisions.jsonl --verify           # both new arms: 3360/3360 OK
npm run view -- --run <opus5> --run <e2b> --run <e4b> --run <gpt56> --out compare-4arms.html
```

## Caveats

- Gold table is **provisional** (unreviewed queue-3 rows); numbers are for plumbing/comparison, not headline claims.
- Identity metrics only — hP/hR granularity scoring is not wired in `evaluate`.
- Committed `decisions.jsonl` for the two new arms are **suspect-filtered** (`grep -v '"op":"suspect"'`): the raw
  logs were 98% `suspect` diagnostic events (114 MB / 98 MB). Suspect ops are counter-only (`replayCore.ts:150`,
  not state-changing), so replay/scoring/view are unaffected — both still verify 3360/3360.
- `compare-4arms.html` is self-contained (open via `file://`, in-page arm switcher).
